# Subway

Substrate/Ethereum JSON-RPC gateway proxy (Rust, `jsonrpsee` + `tokio`). Sits between RPC clients and one or more upstream nodes, adding caching, rate limiting, subscription dedup, param injection, and response validation.

## Entry point & lifecycle

- `src/main.rs` — parses CLI (`src/cli.rs`), reads+validates config, calls `subway::server::build(config)`, then blocks on `handle.stopped()`.
- `subway --config <path>` runs the server. `subway --config <path> validate` only validates config and exits (used in CI/deploy to catch bad config before rollout).
- `src/config/mod.rs::read_config` loads YAML, runs `${VAR}` / `${VAR:-default}` / `${VAR:+word}` env-var templating (regex-based, see `render_template`), then deserializes into `Config`.
- `src/config/mod.rs::validate` runs `garde`-based static validation plus one dynamic check: `rate_limit_weight` must not exceed configured burst sizes, and (if a `client` extension is configured) all upstream endpoints must be reachable.

## Extensions registry (dependency injection)

`src/extensions/mod.rs` implements a type-erased, lazily-built DI container:

- `ExtensionsConfig` is generated by the `define_all_extensions!` macro from a list of `(name, Type)` pairs — this is the single source of truth for which extensions exist: `telemetry`, `cache`, `client`, `merge_subscription`, `substrate_api`, `eth_api`, `server`, `event_bus`, `rate_limit`, `prometheus`, `validator`.
- Each extension implements `Extension::from_config(config, registry)`, may depend on other extensions by calling `registry.get::<OtherExtension>()` (built on first access, memoized in `TypeRegistry`, see `src/utils/type_registry.rs`).
- `ExtensionsConfig::create_registry()` eagerly builds every configured extension at startup by calling `get::<T>()` for each once.
- Extensions not present in the YAML config simply aren't built; code elsewhere treats them as `Option`.

## Middleware chain (request pipeline)

`src/middlewares/mod.rs` defines a generic onion-style middleware chain, parameterized by `Request`/`Result`:

- `Middleware<Request, Result>::call(request, context, next)` — each middleware decides whether/how to call `next` (a boxed closure wrapping the rest of the chain).
- `Middlewares::new(middlewares, fallback)` builds the chain in reverse so the first configured middleware runs first; `fallback` runs if the chain never terminates in a middleware that produces a result.
- `Middlewares::call` spawns the whole chain as a `tokio::spawn`ed task and races it against `tokio::time::sleep(timeout)` via `tokio::select!`; on timeout it calls `task_handle.abort()` and the caller's `oneshot::Receiver` never gets a value (mapped to a `RequestTimeout` error by the caller).
- Two concrete instantiations: `CallRequest`/`CallResult` for methods, `SubscriptionRequest`/`SubscriptionResult` for subscriptions.
- `src/middlewares/factory.rs` maps a middleware name string (from config `middlewares.methods` / `middlewares.subscriptions`) to a concrete builder. **Unknown middleware names panic at startup** (fail-fast, not a runtime path).

### Method middlewares (`src/middlewares/methods/`)

Applied in the order listed under `middlewares.methods` in config. Typical order (see `configs/config.yml`): `delay → response → inject_params → cache → upstream`.

- `response.rs` — short-circuits with a static canned response (config-defined), useful for `rpc_methods`-style stubs.
- `inject_params.rs` — injects a `blockAt`/`blockHash` (Substrate) or `defaultBlock` (Ethereum) parameter so downstream middleware (esp. cache) sees a consistent, cacheable parameter set. **Ordering-sensitive**: README explicitly warns `validate` before `inject_params` causes false positives because the request differs from what's actually forwarded upstream.
- `block_tag.rs` — Ethereum block tag ("latest", "pending", etc.) normalization.
- `cache.rs` — per-method response cache middleware (backed by the `cache` extension / moka).
- `delay.rs` — artificial delay, mostly for testing failure/latency scenarios.
- `validate.rs` — dual-calls a "healthy" reference endpoint and compares responses, logging mismatches — a correctness canary, not meant for production hot path.
- `upstream.rs` — terminal middleware; forwards to the real upstream client.
- `testing.rs` — `#[cfg(test)]`-only middlewares (`crazy`, etc.) used by `src/server.rs` unit tests.

### Subscription middlewares (`src/middlewares/subscriptions/`)

- `merge_subscription.rs` — delegates to the `merge_subscription` extension to dedupe identical upstream subscriptions across multiple downstream clients.
- `upstream.rs` — terminal middleware; opens/forwards the upstream subscription.

## Key extensions (`src/extensions/`)

- `client/` — upstream JSON-RPC client abstraction; supports multiple endpoints with rotation/reconnect on failure (`mock.rs` provides a test double).
- `cache/` — `moka`-backed async cache used by the cache method middleware.
- `rate_limit/` — `governor`-based limiter with three independent dimensions: `connection` (per-connection burst), `ip` (per-source-IP burst, optionally trusting `X-Forwarded-For` via `xff.rs` — **README/config explicitly warns this header is spoofable**), and `weight.rs` (per-method weight, configured via `rate_limit_weight` on each `RpcMethod`, validated against burst size at startup).
- `merge_subscription/` — subscription-dedup engine; `keep_alive_seconds` config controls how long an upstream subscription is kept alive after its last downstream subscriber leaves (in case a new one arrives shortly after).
- `api/` — `substrate.rs` / `eth.rs`: chain-specific helpers (e.g. tracking latest block, `stale_timeout_seconds` health check) built on top of `client`; `value_handle.rs` likely provides shared/await-able latest-value primitives.
- `validator/` — implements the "validate" method middleware's endpoint comparison.
- `server/` — wraps `jsonrpsee`'s server builder: connection limits, CORS, batch size, `http_methods` (plain HTTP GET routes like `/health` mapped to an RPC method — see `proxy_get_request.rs`), and per-request timeout.
- `prometheus/` — metrics endpoint + RPC call metrics (`rpc_metrics.rs`).
- `telemetry/` — OpenTelemetry tracing provider setup (`none`/jaeger/datadog).
- `event_bus/` — internal pub/sub used to decouple extensions (e.g. new-block notifications).

## Config schema (`src/config/`)

- `rpc.rs` — `RpcMethod` (method name, params incl. at-most-one `inject` param and optional-params-must-be-trailing validation, `cache`, `response`, `delay_ms`, `rate_limit_weight`), `RpcSubscription`, alias list `(old, new)`.
- `rpcs:` in config can be a bundled preset (`sub`/`substrate`, `eth`/`ethereum`, `all`/`everything` — baked in via `include_str!` from `rpc_configs/*.yml`), a path to a custom YAML file, or an inline definition with an optional `base` preset that gets overridden/merged (`RpcDefinitionsWithBase` binary-searches and splices method/subscription/alias overrides into the base list).
- `configs/config.yml` is the canonical example (used against HydraDX in this repo's deployment); `rpc_configs/{substrate,ethereum,everything}.yml` are the bundled method/subscription catalogs.

## Utilities (`src/utils/`)

- `type_registry.rs` — the `TypeId`-keyed `AnyMap` used both by the extensions DI container and as the per-request `context: TypeRegistry` passed through the middleware chain.
- `cache.rs` — generic cache helper used by the cache extension.
- `errors` (in `mod.rs`) — canonical JSON-RPC error constructors (`invalid_params`, `failed`, `internal_error`) and `map_error` for translating `jsonrpsee` client errors into server-facing errors.
- `telemetry` (in `mod.rs`) — thin wrapper around `opentelemetry` span creation used uniformly by `server.rs` and the middleware chain.

## Testing & dev workflow

- `make test` / `make test-release` — `cargo test --lib --all`.
- `make clippy` / `make fmt-check` — lint gates (see `.github/workflows/lint.yml`).
- `cargo bench` — Criterion benchmarks in `benches/` (`ws_round_trip`, rate-limit bench).
- `src/tests/` — integration-style tests (`merge_subscription.rs`, `upstream.rs`) spinning up real upstream+downstream `jsonrpsee` servers.
- `tests/configs/` — fixture configs for negative validation tests (`broken_endpoints.yml`, `big_rate_limit_weight.yml`, `config_with_env.yml`).
- `subway --config <path> validate` is the operational pre-flight check — wire it into deploy pipelines before rolling a new config.

## Notable gotchas (see also audit findings)

- `string_to_static_str` in `src/server.rs` intentionally leaks memory (`Box::leak`) once per configured method/subscription/alias at startup. Fine today because `build()` runs exactly once per process; would become an unbounded leak if a config-reload/hot-swap feature is ever added without also reworking this.
- Unknown middleware names in `middlewares.methods`/`middlewares.subscriptions` `panic!` (see `factory.rs`) rather than surfacing as a `validate` error — a typo in config is only caught at `build()` time, not at `subway validate` time.
- `use_xff` rate limiting trusts a client-controlled header unless the deployment's edge/load balancer strips or overwrites it.
